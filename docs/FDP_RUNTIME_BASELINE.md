# FDP Runtime Baseline V10

> Updated: 2026-09-08

This document is the implementation baseline for the current FDP direction.

## 1. Platform scope

FDP is a lightweight deployment and runtime management platform. It does not build source code and does not normalize project internals.

Primary responsibilities:

- browse artifacts produced in Yunxiao Packages;
- download and extract selected artifacts;
- maintain one current deployment directory per project;
- maintain FDP-owned runtime configuration per project;
- create/manage one Docker Container per project;
- manage project environment variables and a fixed database;
- execute SQL against the current project's database;
- start/stop/restart the project manually;
- show current Container logs;
- switch a single external preview entry to one running project.

Explicitly out of scope:

- source-code development;
- Maven/npm builds;
- automatic project-type detection;
- Dockerfile builds as the normal delivery path;
- health checks;
- file/code online preview or editing;
- full deployment history;
- SQL history;
- artifact integrity checking;
- automatic database migration/diffing.

## 2. Project directory model

Each project owns one host directory:

```text
/data/fdp/projects/{projectId}/
├── current/
└── config/
```

`current/` contains the currently deployed artifact contents.

`config/` contains FDP-owned runtime files such as:

```text
start.sh
env.sh
app-start.sh
nginx.conf          # NGINX mode
supervisord.conf     # NGINX mode
```

A new deployment replaces the logical contents of `current/` and keeps `config/`.

The default command working directory is `current/`. A configured work directory is always relative to `current/`.

Inside the Container FDP maps:

```text
current/ -> /workspace
config/  -> /fdp
```

These internal paths are implementation details and should not be exposed as normal user configuration.

## 3. Artifact model

A project may bind multiple Packages artifacts.

Each binding stores:

- repository ID/name;
- artifact name;
- target extraction directory relative to `current/`;
- extraction order;
- deployed version;
- running version.

Deployment order is explicit. Later artifacts may overwrite files extracted by earlier artifacts.

There is no artifact MD5/SHA verification step in V10. The deployment path is intentionally simple:

```text
select version -> download -> extract -> update current -> prepare Container
```

## 4. Deploy and run are separate

Deploy does not start the application.

```text
Deploy
  -> download artifacts
  -> extract into staging
  -> update current/
  -> regenerate config/
  -> create/prepare Container
  -> remain stopped if this is a new Container
```

For an already running Container using the same Runtime Image, artifact deployment does not automatically stop or restart it.

The user explicitly controls:

```text
Start
Stop
Restart
```

After deploy:

- deployed version is updated;
- running version remains unchanged;
- the UI can show `pendingRestart=true`.

After a successful start/restart:

- running version becomes the deployed version;
- pending-restart state is cleared.

If start/restart fails, running version is not advanced.

## 5. Docker model

One project equals one Container.

Container name is generated by FDP:

```text
fdp-project-{projectId}
```

All managed project Containers join the shared Docker network:

```text
fdp-network
```

Restart policy:

```text
unless-stopped
```

FDP manages Container lifecycle. Artifact updates normally reuse the current Container. If Runtime Image changes, the Container must be recreated. V10 refuses to recreate a running Container automatically; the user must stop it first.

## 6. Runtime Images

The platform provides a configurable Runtime Image list.

Default examples:

```text
eclipse-temurin:17-jre
eclipse-temurin:21-jre
node:20-bookworm-slim
node:22-bookworm-slim
```

DIRECT mode works with ordinary runtime images as long as `/bin/sh` and the required runtime exist.

NGINX mode generates `nginx.conf` and `supervisord.conf`. Therefore the selected Runtime Image must contain both `nginx` and `supervisord`; FDP must not assume the stock Java/Node images contain them. Custom runtime images can be supplied through environment configuration.

## 7. Start command

There is no separate deployment command.

The project stores one editable start command, for example:

```bash
java -jar app.jar
```

or:

```bash
node server.js
```

FDP writes the command into project runtime scripts. Editing the command updates `config/`; it does not automatically restart the project.

## 8. Environment variables

Project environment variables are encrypted in the FDP database and materialized into `config/env.sh`.

FDP also injects the fixed database variables:

```text
DB_HOST
DB_PORT
DB_NAME
DB_USER
DB_PASSWORD
```

A project's database cannot be switched after creation.

## 9. Database model

All projects share one MySQL service, but each project has one fixed database.

At project creation:

```text
user enters database name
-> FDP validates identifier
-> FDP checks whether it already exists / is already bound
-> FDP creates database
```

Deleting a project removes the Container and project directory but does not delete the database.

SQL endpoints are scoped to the current project's database only.

V10 supports:

- SQL text execution;
- `.sql` file upload and execution.

It does not store SQL execution history.

## 10. Preview model

Multiple project Containers may run simultaneously.

A single preview Nginx provides the external entry. Switching preview:

```text
select running project
-> write preview nginx config
-> nginx -t
-> reload
```

Switching preview does not stop other projects and does not automatically start the selected project.

The selected preview project ID is persisted in `fdp_platform_setting`.

The server Docker setup must mount the configured preview Nginx file into `FDP_PREVIEW_NGINX_CONTAINER`.

## 11. Schema and API

Migration:

```text
sql/migration_v10_managed_artifact_runtime.sql
```

Primary API prefix:

```text
/api/managed-projects
```

Legacy `/poc-projects` and `/artifact-delivery` APIs remain for migration compatibility.

## 12. Packages download integration boundary

The documented Yunxiao `ListArtifacts` and `GetArtifact` APIs expose artifact/version metadata but do not expose a signed download URL in their response.

For that reason, V10 keeps artifact selection independent from Flow, but the deploy API currently accepts an internally resolved temporary `downloadUrl` together with each selected version. The signed-URL resolver is intentionally isolated as an integration seam.

This must be verified against the actual Yunxiao Packages environment before treating direct Packages download as fully closed. The platform must not reintroduce Flow as the project/deployment data model merely to hide this API gap.
